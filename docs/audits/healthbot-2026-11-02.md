## Розбіжності та ризики, підтверджені кодом

1. **Запис без підтвердження.** `processTool(log_food_intake)` і `log_exercise` одразу викликають create. Немає серверної чернетки та одноразового підтвердження. Повтор операції може створити дубль; для EMBER потрібен унікальний ідентифікатор операції.
2. **Нестабільна історична поживність.** FoodHistory зберігає калорії, але не знімок БЖВ. `get_daily_stats` бере БЖВ з поточного Food. Оновлення/видалення продукту впливає на старий звіт. Зберігати поживність, назву й джерело на момент споживання.
3. **Невідоме прирівнюється до нуля.** Food задає default: 0 для БЖВ. Потрібно відрізняти невідоме, оцінку та відоме значення. Клітковини, цукрів, солі, бренду, джерела й особистої власності немає.
4. **Неоднозначність вибору.** ШІ записує перший продукт за regex назви. Потрібен конкретний підтверджений ID/версія. Неповний запис без грамів чинна схема не підтримує.
5. **Редагування порції.** У PATCH foodHistory перерахунок перевіряє істинність amountG; нуль його обходить. Для оновлення не ввімкнено runValidators. Потрібна послідовна серверна перевірка всіх шляхів запису.
6. **Нагадування суперечать концепту.** Промпт дозволяє автоматично створювати додаткові сповіщення за планами та похвалою. У EMBER потрібне погодження, умови, тихі години й скасування після фактичної дії.
7. **Доставка ненадійна.** Разова задача отримує sent: true до надсилання; збій залишає її начебто надісланою. Повтори захищені Set у пам’яті, часовий пояс залежить від сервера. Динамічні задачі не перевіряють актуальний isBlocked. Потрібні стійкі стани доставки, повторні спроби та захист від конкурентного виконання.
8. **Шаблонні поради.** cron.js містить незмінні повідомлення про час їжі та випадковий вибір чотирьох вправ. Це не погоджена персональна програма з урахуванням стану й обмежень; переносити таку поведінку не пропонується.
9. **Авторизація лише адміністратора.** API захищений adminAuth, адміністратор може працювати із записами різних користувачів. Це очікувано для адмінпанелі, але не замінює особисту авторизацію й ізоляцію даних мобільного/вебклієнта. User вимагає telegramId.
10. **Неповне видалення.** DELETE users видаляє тільки User, залишаючи історії та ScheduledTask. Потрібна повна погоджена процедура очищення.
11. **Тимчасова пам’ять.** Розмови ШІ та стани введення зберігаються в Map. Після перезапуску губляться; у циклі інструментів немає явної межі кроків, місячного бюджету та резервування витрат.

Це статичні висновки; цього разу вони не відтворювалися на справжній MongoDB чи платному API.

## Висновок ПМ / технічна пропозиція

Використати healthBot як джерело вже опрацьованих сценаріїв і кандидатів на повторне використання серверних та адміністративних компонентів. Не вважати його готовим ядром EMBER й не оцінювати готовність відсотком за кількістю файлів.

Наступна задача V1-002: запропонувати архітектуру трьох платформ, серверної БД та локального сховища. Порівняти збереження й розширення MongoDB з альтернативою на основі вимог до історії, рецептів, синхронізації та вартості перенесення. До рішення не переносити й не переписувати дані. Окремо з’ясувати наявність цінних реальних даних, якщо плануватиметься міграція.

Повний склад першої версії залишається чинним. У цьому аудиті не обрано новий стек, не затверджено переписування, не введено Telegram як обов’язкову платформу та не розпочато реалізацію. Відхилення від погодженого концепту спершу виносяться на підтвердження користувача.
